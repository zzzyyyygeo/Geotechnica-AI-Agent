## Day 6（2026-10-15）✅ 数据质量抢救

### 这一天的转折点

原本以为是"继续加功能"，实际做的是**把前 5 天盖在脏数据上的楼拆开重修**。
起因是一次真实体检，发现了 4 个问题：

| # | 问题 | 证据 |
|---|---|---|
| 1 | **扫描版 PDF 的 OCR 文本被拆碎**，检索直接失明 | 「施工缝」「地下工程」「一级防水」在 416 块里命中 **0** 块 |
| 2 | **向量库重复入库** | `embeddings` 表 1248 条，而文档只有 416 块（跑一次加一份） |
| 3 | **答案没有出处** | 只返回 AI 的话，不知道依据第几页第几条 |
| 4 | **API Key 明文写在代码里** | 2 个 key 出现在 6 个文件中 |

### 学到的东西

1. **RAG 分层诊断**：检索层和生成层必须分开测。
   80% 的"答不准"其实是检索层的问题，改 Prompt 没用。
2. **中文 OCR 文本清洗**（正则实战）：
   - `(?<=[\u4e00-\u9fff])[ ]+(?=[\u4e00-\u9fff])` 用零宽断言修汉字间的空格
   - 必须循环替换，因为「工 程 防 水」一次只删一个空格
   - **清洗顺序很关键**：汉字粘连 → 去噪声 → 数字归一化 → 标点整理
3. **清洗的边界（诚实认知）**：
   - ✅ 「4 ． 1 ． 2 1」→「4.1.21」能修（空格/换行破坏）
   - ❌ 「3 O O」（OCR 把 0 认成字母 O）永远修不了 → 只能换电子版文档
4. **结构化切分**：按规范条文号（4.1.16 这种）切，而不是按 500 字符硬切。
   条文天然是语义完整单元，且能直接给出来处。
5. **幂等入库**：稳定 id + 先查后补，跑 10 次和跑 1 次结果一样。
6. **带出处的回答**：把页码/条文号塞进 Prompt 并要求模型标注依据。
7. **工程素养**：API Key 走环境变量；Windows 控制台 GBK 会炸 emoji，要
   `sys.stdout.reconfigure(encoding="utf-8")`。

### 量化成果

| 指标 | 清洗前 | 清洗后 |
|---|---|---|
| 关键词「地下工程」命中块数 | 0 | **132** |
| 关键词「施工缝」命中块数 | 0 | **40** |
| 关键词「一级防水」命中块数 | 0 | **1** |
| 知识库结构 | 416 块糊在一起的碎渣 | **654 条规范条文**，572 条（87%）带条文号 |
| 检索关键词覆盖率（8 题测试集） | 无法测（关键词都搜不到） | **90.6%** |
| 平均检索距离 | — | **0.4239** |
| 重复入库 | 1248 条 vs 416 块 | **第二遍运行新增 0 条** |
| 答案出处 | 无 | 页码 + 条文号 |

### 遗留问题（已定位，Day 7 解决）

1. **条文切得太碎，反而丢了上下文**：
   问"防水等级分为几级"，Top1 检回的是「3.2.2 ...按表 3 」，句子是断的。
   → 答案在「3.2.1 + 表 3.2.2」里，需要**父文档返回**（小块匹配、大块喂给模型）。
2. **纯向量检索对精确条款号不敏感**：问「第 5.1.13 条」这种，向量不如关键词好使。
   → 需要**混合检索（BM25 + 向量）**。
3. **OCR 错字残留**：实测「3 O O」仍出现 7 次（本应是 300mm）。
   → 需要换现行规范的**电子版**文档（见下）。
4. **规范版本过期**：GB 50108-2008 已被 **GB 55030-2022**（2023-04-01 实施，全文强制）部分替代。
