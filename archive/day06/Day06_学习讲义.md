### 2.1 第一步永远是：分层诊断

RAG 出问题，新手只会说"答得不准"，然后开始瞎调 Prompt。正确做法是把它拆成两段测：

```
用户问题 → [检索器] → 检回的文本 → [生成器] → 答案
             ↑ 先测这里              ↑ 再测这里
```

**检验标准（今天你必须记住）：**

| 现象 | 病因 | 该改哪 |
|---|---|---|
| 相关文本**根本没被检回** | 数据/切分/检索层 | 修数据、调 chunk、加混合检索 |
| 相关文本检回了但**答不对** | 生成层 | 改 Prompt、换模型 |
| 检回了、答案也对，但**不知道哪来的** | 产品层 | 加出处引用 |

我在 `03_诊断_检索与生成分层测试.py` 里给你写了这个诊断工具。
**这是你今天最该带走的一个工程习惯**：先量,再改。

### 2.2 中文 OCR 文本清洗（今天的重头戏，正则实战）

原理很简单：**OCR/PDF 提取会把"排版信息"误当成"内容"**，
表现为汉字之间插空格、标点单独成行、目录点线混入正文。我们要反向修复：

```python
import re

CN = r"\u4e00-\u9fff"          # 一个汉字的范围

def clean_ocr_text(text):
    t = text
    # 1) 汉字 + 换行 + 汉字 → 粘回去（跨行断字，最常见的碎法）
    t = re.sub(rf"(?<=[{CN}])[ \t\u3000]*\n[ \t\u3000]*(?=[{CN}])", "", t)
    # 2) 汉字 + 空格 + 汉字 → 粘回去（要循环做，处理「工 程 防 水」三连）
    prev = None
    while prev != t:
        prev = t
        t = re.sub(rf"(?<=[{CN}])[ \t\u3000]+(?=[{CN}])", "", t)
    # 3) 标点前不该有空格
    t = re.sub(rf"(?<=[{CN}])[ \t\u3000]+(?=[，。、；：？！）】》])", "", t)
    # 4) 标点被单独扔到一行 → 并回上一行
    t = re.sub(r"\n+(?=[，。、；：？！])", "", t)
    # 5) 目录点线
    t = re.sub(r"[…\.·]{4,}", " ", t)
    t = re.sub(r"\n{2,}", "\n", t).strip()
    return t
```

**三个必须理解的正则概念：**

| 写法 | 名字 | 作用 |
|---|---|---|
| `(?<=X)` | 后向肯定断言 | 前面必须是 X（但不吃掉 X） |
| `(?=Y)` | 前向肯定断言 | 后面必须是 Y |
| `[ \t\u3000]+` | 字符类 + 量词 | 一个及以上空格/制表符/全角空格 |

> 这三招是文本处理的通用武器，不是本项目专属。面试问"你怎么处理脏文本"，
> 能答出"用零宽断言做中文粘连修复"就是加分项。

**效果（我用你的真实数据跑出来的）：**

| 关键词 | 清洗前命中块数 | 清洗后命中块数 |
|---|---|---|
| 地下工程 | **0** | **129** |
| 施工缝 | **0** | **44** |
| 一级防水 | **0** | **1** |
| 防水混凝土 | 20 | 66 |

同一个问题的 Top-1 检索结果，清洗后从：

```

变成：

```

防水混凝土结构自防水其防水效果尚好，而细部构造，特别是施工缝、变形缝的

### 2.3 分块策略：为什么你现在的切法是下策

你用的是 `RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)`，
但切分发生在**清洗之前**，所以：

- 一句话被从中间劈开："部位宜采用十字配" | "件(图5.1.12—1)"
- 表格被拆成散字（"1 缝 内两侧基 面"）
- 目录页、图注也被当成正文入库

**正确顺序（今天的核心工程洞察）：**

```
PDF → 提取文本 → 【清洗归一化】 → 去掉目录/图表噪声 → 【再切分】 → 入库
                    ↑ 你现在缺这一步
```

三种切法对比（面试会问）：

| 切法 | 怎么切 | 优点 | 缺点 |
|---|---|---|---|
| 固定长度 | 每 500 字一刀 | 实现最简单 | 切断语义，最差 |
| 递归字符（你在用） | 按 `\n\n`→`\n`→`。` 优先级切 | 比固定长度好 | 依赖文本本身结构好 |
| **结构化/语义切分（推荐）** | 按"第 X 章 / X.Y 条"切 | 条文完整，能直接给出处 | 要写正则，费点功夫 |

对规范类文档，**最优解是按条文号切**：`5.1.13`、`4.1.4` 这种编号天然就是语义单元。
这样检索出来能直接说"依据第 5.1.13 条"，专业度立刻不同。

### 2.4 幂等入库：重复运行不能产生重复数据

你现在的写法：

```python
# ❌ 每次运行都再插一遍 → 1248 条
vectorstore = Chroma.from_documents(documents=docs, embedding=embeddings,
                                    persist_directory="./chroma_db")
```

改成"先查、后补"：

```python
# ✅ 只补新增的，重复运行不会变脏
vectorstore = Chroma(persist_directory=DB_DIR, embedding_function=emb)
existing = set(vectorstore.get(include=[])["ids"])      # 已经在库里的 id
new_docs, new_ids = [], []
for i, doc in enumerate(docs):
    cid = f"gb50108-{i}"                                # 稳定 id：内容不变则 id 不变
    if cid not in existing:
        new_docs.append(doc)
        new_ids.append(cid)
if new_docs:
    vectorstore.add_documents(documents=new_docs, ids=new_ids)
```

**"幂等"这个词你今天就记住**：同一段代码跑 1 次和跑 10 次，结果一样。
这是工程代码和脚本的分水岭，面试爱问。

> 为什么用**稳定 id** 而不是随机 id：内容不变 → id 不变 → 重跑时能识别出"这条已经有了"。

8. 清洗解决不了 OCR 的哪类错误？那该怎么办？

<details>
<summary>答案</summary>

1. 先把检索结果单独打出来看：相关段落有没有被检回。
   没检回 → 改数据/切分/检索；检回了但答错 → 改 Prompt/换模型。
2. 把「汉字 空格 汉字」中的空格删掉，即修复 OCR 把中文词拆开的问题。
   `(?<=...)` 是后向断言（要求前面是汉字但不消耗），`(?=...)` 是前向断言。
3. 因为「工 程 防 水」一次替换只能删掉一个空格（重叠匹配问题），
   循环到不再变化才能全部粘连。
4. 切分先做会把一句话从中间劈开，清洗时已经无法跨块修复；
   先清洗再切分，才能保证每个块内部是完整语句。
5. 同一段代码运行多次，结果与运行一次相同。实现方式：给每块分配稳定 id，
   入库前先用 `collection.get(include=[])["ids"]` 查出已有 id，只添加新 id。
6. 稳定 id：内容没变则 id 不变，重跑时会被识别为"已存在"，不重复插入；
   随机 id：每次都是新 id，重跑必然产生重复数据（你现在的 1248 条就是这么来的）。
7. 规范条文答错要负责任；给出处让用户可复核、可引用，也让模型幻觉无处藏身；
   工程交付物必须可追溯。
8. 解决不了"字符认错"，例如 700 被认成 7 O 0、生僻字被认成别的字。
   只能换电子版（可复制文字）的 PDF/DOCX，或用专业 OCR 重新识别。

| 缺口 | 为什么必须补 | 建议时机 |
|---|---|---|
| **评估能力**（RAGAS / 自建测试集） | 面试必问"你怎么知道你的 RAG 变好了"，答不出就露馅 | Day 8 |
| **Python 工程基础** | 你现在靠"能跑就行"，遇到报错就卡住 | 每天 30 分钟，穿插进行 |
| **数据库/mysql + 部署** | 作品要能上线，不能只在自己电脑上跑 | Day 10 之后 |

> 面试最常被追问的一句是："**你怎么评估你的系统效果？**"
> 今天你做的"用量化指标对比清洗前后命中率"，就是这个问题的标准答案雏形。
